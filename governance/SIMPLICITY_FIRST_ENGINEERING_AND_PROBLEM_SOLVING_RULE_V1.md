# Simplicity-First Engineering and Problem-Solving Rule V1

## Status

`USER_FIXED__PROJECT_WIDE_BINDING_RULE__ALL_DEVELOPMENT_PHASES`

This rule applies to First Launch, V0, mainline development, research, product planning,
engineering optimization, Project Control, implementation, review, deployment, operations,
incident response, recovery and future higher-authority trading work.

It is not limited to one notification incident or one release stage.

## Binding objective

After the minimum real safety, authority, correctness and recovery boundaries are preserved, every
problem must be solved through the simplest viable route.

"Simple" means the lowest total burden across:

- implementation time;
- operator actions and attention;
- debugging and evidence collection;
- review and testing;
- deployment and rollback;
- maintenance and recurring operations;
- third-party dependencies, quotas, credits and outage exposure;
- future replacement and migration cost.

A method that writes little code but requires many uncertain UI steps, long manual payloads,
repeated screenshots or repeated trial-and-error is not a simple method.

## Mandatory simplicity gate before work starts

Every task contract, implementation plan or diagnostic plan must answer:

1. What is the single exact outcome or question for the current step?
2. What already-existing command, capability, provider-native interface or accepted component can
   answer it?
3. What minimum safety and authority boundaries cannot be removed?
4. What is the route with the fewest components, hops, credentials and operator actions?
5. What is the expected total cost, including user operation, diagnosis, review, maintenance and
   failure recovery?
6. What are the success condition, failure condition, maximum attempts and replacement route?
7. Which proposed components are optional and therefore prohibited from entering the current
   critical path?

Work must not begin when these questions are materially unanswered.

## Preferred solution order

Use the first safe option that can satisfy the accepted requirement:

1. reuse an existing accepted capability or command;
2. use a direct provider-native interface, API or webhook;
3. use a short checklist or one-off command;
4. use a minimal task-specific script or adapter;
5. use a maintained external tool only when it reduces total complexity rather than merely moving
   complexity into another UI or service;
6. create a small permanent component only after repeated use or a critical requirement proves its
   net value;
7. introduce a service, framework or institution-grade subsystem only when scale, authority,
   reliability or compliance objectively requires it.

A generic relay, workflow platform or extra service must not be inserted between two systems when
a safe direct integration is available with a bounded adapter.

## Minimum-verification ladder

Testing and diagnosis must proceed from the smallest decisive test to the largest:

1. one component or direct connectivity test;
2. one bounded pairwise integration test;
3. the minimum required failure-semantics test;
4. the controlled end-to-end test;
5. broader regression only when the changed boundary requires it.

Do not begin with a complete multi-component workflow when a smaller test can answer the current
question.

Synthetic test data should be built into the test or generated by a small command. The operator
must not be asked to paste a long production-shaped payload unless that exact payload boundary is
the subject of the test and no simpler fixture can prove it.

## Third-party UI rule

Third-party interfaces change and may differ by account, plan, region or editor mode.

Therefore:

- do not issue instructions based only on an assumed or remembered UI;
- use the user's current screenshot or live interface as the evidence for available controls;
- syntax highlighting, button inactivity or layout differences are not proof of a code defect;
- a third-party UI must not be the only available validation path when a direct API, code step,
  provider-native test or command can answer the question more reliably;
- do not make the operator repeatedly search for missing controls;
- do not require repeated copying of secrets, tokens, webhook URLs or large payloads.

If the shown UI does not match the proposed instructions, stop and reassess the route instead of
inventing additional clicks.

## Two-attempt route stop-loss

For one bounded route:

- the first failure permits evidence-based diagnosis and one targeted correction;
- the second failure requires an explicit decision to replace, reduce or abandon that route;
- after two failed attempts, continuing the same interaction pattern is prohibited unless new
  evidence proves that one small, specific correction will close it immediately.

Sunk time, partial setup or prior implementation effort does not justify continued work on a route
that is now more complex than an available replacement.

Repeated variants of the same ineffective instruction count as attempts. Renaming a button search,
reformatting the same payload or asking the operator to retry the same UI action does not create a
new route.

## Operator-interaction budget

Each normal execution stage should require no more than one to three clear operator actions unless
the accepted safety boundary objectively requires more.

Every instruction packet must state:

- the exact action;
- the expected visible result;
- what evidence may be shared without secrets;
- when to stop;
- what the next route is if it fails.

Instructions must not ask the operator to infer whether colored text is an error, repeatedly test
an unresponsive button, or navigate uncertain controls without a bounded fallback.

## Third-party dependency and credit gate

Before placing a third-party service on a critical path, determine and record:

- whether it consumes credits, tasks, events, invocations, bandwidth or another quota;
- the current plan and available allowance, when this can be verified safely;
- behavior when the allowance is exhausted;
- outage, suspension, rate-limit and account-lock risks;
- credential scope and rotation procedure;
- whether a direct or self-contained alternative is simpler;
- whether the service is temporary, replaceable or part of an accepted long-term architecture.

Unknown quota or credit behavior is a deployment risk. It must not be ignored merely because the
initial setup succeeds.

A third-party tool is acceptable only when its total operating burden and failure surface are
lower than the direct or custom alternatives for the accepted stage.

## Complexity exception

Additional complexity is allowed only when it protects a concrete boundary such as:

- trading or execution authority;
- financial risk control;
- credential and secret protection;
- data freshness or integrity;
- durable evidence and idempotency;
- rollback and recovery;
- regulatory or contractual obligations;
- a measured scale or availability requirement.

The task contract must identify the exact boundary, why the simpler option is insufficient and the
smallest added mechanism that closes the gap. "More complete", "more professional" or
"institution-grade" is not sufficient justification.

## Mandatory review checks

A reviewer must reject or return a plan when it:

- solves several unrelated questions in one first test;
- adds an avoidable platform, relay, daemon, framework or service;
- requires uncertain third-party UI behavior without a fallback;
- makes the operator paste or edit large payloads unnecessarily;
- lacks success, failure, stop and replacement conditions;
- repeats the same failed route beyond the permitted attempts;
- counts only code-writing time while excluding operator, review, maintenance or recovery cost;
- moves complexity to the user or an external service and then labels the result "no-code" or
  "simple";
- builds future capability before the current accepted need is closed;
- preserves a route only because prior effort has already been spent.

## Required task and completion reporting

Every material task must include a compact `SIMPLICITY_GATE` section recording:

- exact current question;
- selected minimum route;
- components and external dependencies;
- estimated operator actions;
- total implementation and calendar cost;
- maximum route attempts;
- success, failure and replacement conditions;
- alternatives rejected and why;
- intentionally deferred functionality.

Every completion or failure report must state:

- the route actually used;
- observed attempt count;
- what was simplified or removed;
- residual complexity and recurring burden;
- any quota, credit or third-party dependency still present;
- the next safe action, if the outcome is incomplete.

## Incident record: Pipedream workflow testing

The project attempted to validate a Pipedream-to-Discord route through a complex Trigger test-event
UI that required a long production-shaped payload and controls that were unavailable or
unresponsive in the operator's actual interface.

The JSON was valid, but the diagnostic route combined too many boundaries and treated uncertain UI
behavior as the primary path. Repeated attempts consumed operator time without answering the core
question.

A later isolated Code Step tested the actual question directly: whether the saved credential could
create and confirm a Discord message. That method was materially simpler and should have been used
first. The user subsequently selected removal of the unnecessary relay in favor of a bounded direct
Discord integration.

Binding lessons:

1. isolate one question;
2. prefer direct tests and direct integrations;
3. do not rely on assumed third-party UI;
4. do not require long manual test payloads when a fixture can be embedded;
5. stop the route after two ineffective attempts;
6. replace a more complex route immediately when a simpler safe route is identified.

## Enforcement

This rule applies to every AI participant, human contributor, product planner, engineering lane,
reviewer and successor window.

A violation requires the active lane to safe-stop, preserve evidence, reduce or replace the route
and update the task contract before continuing.

No First Launch, V0 or mainline urgency waives the rule. Urgency strengthens the requirement to
choose the smallest safe route; it does not authorize uncontrolled shortcuts or unnecessary
complexity.
